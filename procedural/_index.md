# procedural

## Knowledge pages in this domain

- [demo-generation](demo-generation.md) — The standalone demo generation workflow (a six-step loop): understand the requirement → technical design → create the project → write the code → verify the build → capture documentation. Applies when the user directly asks to "write a demo" / "generate a test project" and similar standalone demo scenarios. Distinct from the reproduction demos generated within framework issue analysis.
- [fetch-ohos-third-party-lib](fetch-ohos-third-party-lib.md) — One-command download of arm64-OpenHarmony prebuilt bottles (.so) from Harmonybrew, with checksum verification and extraction, so you can link them into a Qt HarmonyOS project without cross-compiling. Covers recursive dependencies, qmake/CMake link snippets, and version-resolution pitfalls.
- [framework-fix-verification](framework-fix-verification.md) — The framework fix verification workflow: obtain the verification checklist → write the verification project → verify manually → record the results. Used to systematically verify that Qt framework bug fixes work.
- [framework-issue-analysis](framework-issue-analysis.md) — The framework-internal issue analysis workflow (a four-phase loop): generate a reproduction demo → iterate on build fixes → localize the problem (via logs) → root cause analysis (framework code call chains) → verify the system interface → package and submit an upstream issue (the workflow's final step). Phase four is the closing point: produce a clean patch, prepare the issue write-up, output a pure-Qt reproduction demo, and update the knowledge base index. Applies to analyzing Qt framework bugs on HarmonyOS.
- [llvm-ohos-cross-compile](llvm-ohos-cross-compile.md) — The adapter for consuming OHOS arm64 LLVM 15 static libraries from Qt/QLogo: which libraries the Qt target links, the library closure QLogo's JIT needs, deployment, and regression checks. The general OHOS NDK/LLVM cross-compilation process is maintained in the common knowledge base.
- [qt-app-harmonyos-completion](qt-app-harmonyos-completion.md) — The application-polish workflow for HarmonyOS porting (a feature-level test case loop, four phases): scan the application source to identify core features → generate 10 core test cases (AI scans the source + human review) → loop through manual testing / reporting problems / fixing / regression → close once all 10 cases pass. Prerequisite: the run test (qt-ohos-run-test) passes. Includes the standard trio (ASCII loop diagram / loop exit condition ✅ all 10 cases pass / gate checks ⚠️).
- [qt-app-harmonyos-full-pipeline](qt-app-harmonyos-full-pipeline.md) — Stitches the scattered Qt-to-HarmonyOS workflows into a single end-to-end orchestration: the common library supplies the canonical facts about the HarmonyOS lifecycle, windows, and platform limitations, and this page maps them onto the 8 phases of Qt migration, building, signing, deployment, testing, and store submission. Covers Qt 5.12/5.15/6.12 and flags the gaps in Qt 6 end-to-end run+test and application distribution.
- [qt-app-harmonyos-migration](qt-app-harmonyos-migration.md) — The Qt application HarmonyOS migration workflow: assess feasibility → create the project structure → migrate step by step through an 8-step decision tree → verify the build → capture the knowledge. The end-to-end process for migrating a Qt application from another platform to HarmonyOS.
- [qt-bug-report-generation](qt-bug-report-generation.md) — The bug report generation workflow: extract information from the conversation context or an existing problem page → fill in the embedded template → self-check reproducibility (a HARD gate) → produce two forms (form A, a complete deliverable for Huawei / form B, a condensed version for an issue tracker). External partners can learn to write a bug report from this page plus the sample page alone; the template structure is embedded here and doesn't depend on any internal template file.
- [qt-bug-report-sample](qt-bug-report-sample.md) — Sample (form A): a Qt 5.15 HarmonyOS application crashes because a bare eval of @ohos.deviceInfo is rejected by the ArkTS runtime when onAcceptWant fires; triage concluded it was the Qt framework (a stale glue template that didn't eager-import the registered module), and it was fixed on the Qt side.
- [qt-cef-ohos-dev-guide](qt-cef-ohos-dev-guide.md) — The Qt + CEF HarmonyOS development guide (public, self-contained, version-neutral): HarmonyOS Qt has no QtWebEngine (out of scope), and CEF for OpenHarmony (chromium_cef) is the full-Chromium-kernel web embedding replacement. **Not tied to a specific Qt version** (works with Qt 5.12/5.15/Qt 6; adapt by reading your Qt OHOS SDK headers per §5.1). CEF is delivered as a **de-versioned component package** — the maintainers strip the kernel layer (libcef.so + wrapper + include + cmake + OHOS adapter) out of chromium_cef's versioned downloads, tag it by version, decouple it from applications/glue, and place it where developers can download it; the integration is version-neutral (find_package(CEF) + CEF_ROOT, reading the component's include/ to find that version's API). Part 1 is the version-stable core; Part 2 is an integration example (given a CEF component package + your Qt OHOS SDK). Includes a WebEngine→CEF API mapping, migration steps, and a §5 methodology for adapting to version upgrades.
- [qt-ohos-run-test](qt-ohos-run-test.md) — The HarmonyOS run-test workflow (a full CLI pipeline, a seven-phase loop): environment/SDK pre-check → static build pre-check (DT_NEEDED / symbol visibility / QML plugin deployment) → sign and install → launch and run-time testing (localizing the three classes of black-screen rendering failure / Ability lifecycle exit / window behavior regression / input events / platform limitation regression) → crash log analysis → fix and regress → Playbook B demo. Focused on getting the application running on a real device, not full functional verification (for the feature-case loop, see the application-polish workflow). Includes the standard trio (ASCII loop diagram / loop exit condition ✅ / gate checks ⚠️). Reused by application porting, build troubleshooting, and fix verification.
- [qt6-ohos-manual-deploy](qt6-ohos-manual-deploy.md) — A manual deployment process that works around the 5 deployment defects in harmonydeployqt6 (Qt 6.12 Beta2): copy the DevEco project skeleton from the SDK templates + manually deploy the business .so + libqohos + the Qt 6 runtime + the QML module qmldir + the QML plugin .so + the QML plugin's Qt 6 dependencies into the right locations (libs/ vs resfile/qml/) + configure APP_LIBRARY_NAME + build with signing. harmonydeployqt6 is never invoked.
- [qt6-ohos-windows-cli-deploy](qt6-ohos-windows-cli-deploy.md) — Building a Qt project end to end from the Windows command line with a prebuilt-installer Qt 6.12.0 Beta2 and generating a HarmonyOS DevEco project: the official wiki CLI workflow (qt-cmake → cmake --build → harmonydeployqt6 → sign in DevEco and install on the device) + this machine's actual paths (${QT6_INSTALL_ROOT}, the ${DEVECO_STUDIO} junction, API 23 native) + what the prebuilt build saves you from patching (NEEDED entries are already bare names, qt_add_executable makes main GLOBAL DEFAULT automatically). Fills in what the wiki doesn't cover: QT_CHAINLOAD_TOOLCHAIN_FILE being mandatory, the DevEco whitespace pitfall, the one-shot _make_hap target, and the six signing artifacts.
