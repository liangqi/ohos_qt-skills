### 0、铁律

**⚠️ 元铁律：以下两条在所有其他铁律之上，每次交互必须首先执行**

**铁律 α — 铁律回顾机制**

每次回答用户问题或开始任何任务前，必须先在内部逐条回顾本章节所有铁律，自查当前动作是否存在违规风险。

| 违规行为 | 正确做法 |
|---------|---------|
| 收到用户消息后直接开始执行任务 | 先内部过一遍铁律清单，确认无冲突后再动手 |
| 只记得部分铁律就开始操作 | 完整回顾：流程顺序、禁止推测、知识库优先、平台隔离、源头优先、沉淀修复、门禁通过、依赖盘点、用户交互、文件操作纪律 |

**铁律 β — 文件操作纪律**

对项目中任何文件的**写入、修改、删除**操作，必须严格遵守本 skill 的流程规则。**严禁**脱离流程自行决定改动。
| 任何文件 | 严禁未经流程授权的预防性修改（"我觉得这里以后可能出问题所以先改了"）|

| 违规行为 | 正确做法 |
|---------|---------|
| 还没到对应步骤就提前修改文件 | 按步骤顺序推进，当前步骤未完成前不碰下一步骤的文件 |
| 为了"方便"跳过记录直接改代码 | 每次改动必须有流程依据、有错误证据、有沉淀记录 |
| 删除或覆盖已有的修复记录/环境记录 | 只追加不删除，历史记录是后续排错的依据 |

**严格按照skill的流程执行每一步、不许跳步骤、也不许脱离skill计划自己执行**

**警示信号**

当你发现自己有以下想法时，立即停止：

- 仅凭文档就下结论

- 假设其他平台的行为也适用于OHOS

- 没有阅读实际源代码

- "这应该和windows一样..."

- "我觉得依赖可能是..."

**捕获到这些信号 → 停止。回去读代码。**

**遇到问题，优先查询 `compile_fix_pro.md`**

| 触发时机 | 执行动作 |
|---------|---------|
| 编译 / 链接 / 打包 / 运行出现任何错误 | **第一步**：在 `compile_fix_pro.md` 中搜索是否已有匹配的解决方案 |
| 找到匹配方案 | 直接按方案执行修复，不再重复分析 |
| 未找到匹配方案 | 按正常流程分析问题，修复后将新方案**追加写入** `compile_fix_pro.md` |

> ⚠️ 跳过知识库查询直接分析问题 = 违规。已解决过的问题不应浪费时间重新分析。

**平台分支必须显式隔离**

| 违规行为 | 正确做法 |
|---------|---------|
| 直接修改通用逻辑适配 OHOS | 用 `#if defined(Q_OS_OHOS)` / CMake `if(OHOS)` / qmake `ohos:` 条件隔离 |
| 改动导致 Linux/Windows/macOS 原逻辑不可用 | OHOS 改动必须封闭在条件分支内，不影响其他平台 |

**只改源头，不优先改生成物**

| 违规行为 | 正确做法 |
|---------|---------|
| 修改 build 目录下的 Makefile 或临时产物 | 优先改 CMakeLists.txt、.pro、源码、模板配置 |
| 把构建中间产物当交付件提交 | 所有改动必须追溯到源头文件 |

**修复成功必须沉淀**

| 触发时机 | 执行动作 |
|---------|---------|
| 任何编译 / 链接 / 打包 / 运行问题修复成功、| **必须**修复超过三个问题时必须先把之前修复的问题追加到 `compile_fix_pro.md`，包含：错误原文、发生阶段、根因、改动文件、验证命令 |

**门禁失败禁止标记成功**

| 检查项 | 未通过时 |
|-------|---------|
| 编译产物缺失 / HAP 未生成 | ❌ 不能写"完成" |
| 安装失败 / 启动失败 | ❌ 不能写"完成" |
| Qt .so 缺失 / RPATH 不完整 / 依赖断裂 | ❌ 不能写"完成" |

> 只有全部门禁通过，才能标记步骤完成。

**依赖先盘点，缺失不可猜**

| 违规行为 | 正确做法 |
|---------|---------|
| 假设某个 Qt 模块 / 三方库 / SDK 存在 | 在 `qt_env.md` 中明确记录每项依赖的状态（☑ 已就绪 / ☐ 缺失） |
| 跳过盘点直接编译 | 先完成 §3 依赖环境梳理，所有项状态明确后再进入编译 |

**平台能力限制要降级，不要硬绕**

| 违规行为 | 正确做法 |
|---------|---------|
| 对同一个平台限制反复重试同一命令 | 确认是平台限制后，记录限制原因，选择替代方案或功能降级 |
| 例：syscall / 权限 / 文件系统 / 动态库加载限制 | 记录到 `qt_env.md`，标注为「平台限制」并给出降级策略 |

**自动检测 MCP 是否安装**：

通过尝试调用 MCP 工具验证工具链是否可用：

| 检测方式 | 检测动作 | 判定结果 |
|---------|---------|---------|
| 调用 MCP 工具 | 尝试调用 `deveco-mcp` 的工具（如 `harmonyos_knowledge_search` 或 `build_project`） | 成功返回 → ☑ 已安装；工具不存在/调用失败 → ☐ 未安装 |
| 检查工具可用性 | 查看当前会话中是否有 `deveco-mcp_*` 相关工具 | 存在 → ☑ 已安装；不存在 → ☐ 未安装 |

**检测流程**：

```
1. 尝试调用 deveco-mcp 工具（如 harmonyos_knowledge_search 搜索关键词 "test"）
2. 如果调用成功 → MCP 已就绪，标记 ☑，记录检测时间到 qt_env.md
3. 如果调用失败（工具不存在）→ MCP 未安装，进入安装引导流程
```

根据检测结果进入对应分支：

| 检测结果 | 处理方式 |
|---------|---------|
| ✅ MCP 已安装且可用 | 记录到 `qt_env.md` 标记 ☑ 及检测时间（格式：YYYY-MM-DD HH:mm），继续 1.2 |
| ❌ MCP 未安装或不可用 | 引导用户阅读 `build-run-qt-app` skill 的「前置条件：DevEco MCP工具链安装配置」章节完成安装。**暂停本流程，等待用户回复安装结果** |

### 3、依赖环境

**3.0 梳理当前项目的用途**

- 阅读项目的 README.md、官方文档或源码注释
- 明确项目的**核心功能**（例：代码编辑器组件、图表库、协议解析库）
- 明确项目的**目标产物类型**（动态库 / 静态库 / 可执行文件）
- 产出：一段 2-3 句话的项目摘要，追加到 `qt_env.md`

**3.1 Qt 版本依赖**

- 确认项目依赖的 Qt 大版本（Qt5 / Qt6）
  - 若为 Qt5，确认最低兼容的小版本号
  - 若为 Qt6，执行以下降级评估流程：

**Qt6 → Qt5 降级评估流程**

> 背景：当前鸿蒙化 Qt 分支仅支持 Qt5（5.12.12 / 5.15.16），若项目使用了 Qt6，需评估是否可降级到 Qt5 版本。

**Step A：检测是否使用了 Qt6 独有特性**

在源码和构建文件中搜索以下 Qt6 特征，任一命中即判定为"使用了 Qt6 独有特性"：

| 检测项 | 搜索方式 |
|--------|---------|
| Qt6 专属模块 | grep 构建文件中的 `Qt6::` / `find_package(Qt6` / `QT += core5compat` |
| Qt6 CMake API | grep `qt_add_qml_module` / `qt_add_executable` / `qt_add_resources` |
| Qt6 独有头文件/类 | grep `#include <QPromise>` / `QFuture::then` / `QStringView` 的 Qt6 新 API |
| QML 变更 | grep `import QtQuick` (无版本号写法为 Qt6 风格) |
| C++17 强依赖 | 结合 `CMAKE_CXX_STANDARD 17` 和 Qt6 API 同时出现 |

- 若**未命中**任何 Qt6 独有特性 → 项目本身兼容 Qt5，直接按 Qt5 流程继续
- 若**命中** → 进入 Step B

**Step B：查找仓库中的 Qt5 版本**

在当前仓库中查找可能的 Qt5 兼容版本：

```bash
# 查找含 qt5 / Qt5 / 5.x 的分支
git branch -a | grep -iE 'qt5|5\.[0-9]+'

# 查找含 qt5 / Qt5 / 5.x 的 tag
git tag -l | grep -iE 'qt5|5\.[0-9]+'

# 如果没有明确命名，查看所有 tag 的时间和描述
git tag -l --sort=-creatordate | head -20
```

- 若**未找到**任何 Qt5 分支或 tag → 记录到 `qt_env.md`："仓库无 Qt5 版本，需手动适配降级"，**向用户报告并等待决策**
- 若**找到**候选分支/tag → 按以下优先级选取后进入 Step C

**选取优先级**（tag 和分支同时存在时）：

> tag 是不可变的版本快照，代表作者在某个时间点明确标记的发布状态；分支则可能持续变动。因此 **tag 优先于分支**。

| 优先级 | 类型 | 理由 |
|:---:|------|------|
| 1️⃣ | **tag**（如 `v1.2.3`、`qt5-stable`） | 不可变快照，版本语义明确，可复现性最强 |
| 2️⃣ | **release 分支**（如 `release/1.x`、`stabl**4.5 总结文档输出**

> 前置条件：§4.4 验证清单全部 ☑ 后方可进入本步骤。

**🔐 双重交验协议（适用于「编译构建无错误」与「HAP 安装启动无错误」）**

> 每个验证项必须独立完成两轮验证，任一轮未通过即判定该项 ❌。禁止合并两项、禁止跳过任何一轮。

**第一轮：AI 自动审查（日志审查）**

| 步骤 | 执行动作 | 判定标准 |
|:---:|---------|---------|
| 1 | 获取完整构建/安装日志（不截断） | 日志成功获取 |
| 2 | 在日志中搜索以下**失败关键词**：`ERROR`、`FAILED`、`fatal`、`undefined reference`、`cannot find`、`No such file`、`BUILD FAILED`、`Install Failed`、`crash`、`SIGSEGV`、`SIGABRT` | 逐一记录命中项 |
| 3 | 对每个命中项进行**误报排除**：是否属于注释/文档描述中的文字、是否为已忽略的已知警告、是否为依赖库内部日志但不影响产物 | 仅保留真实错误 |
| 4 | 输出第一轮审查结论 | 「无真实错误」或「发现 N 个错误：\<列表\>」 |

> ⚠️ 搜索关键词必须**逐个执行**，不得仅凭"看了一眼日志没发现问题"就跳过。每个关键词的搜索结果（命中数或零命中）需可追溯。

**第二轮：用户确认（人工交验）**

> 第一轮完成后（无论结果如何），必须将审查结论**完整展示**给用户，并明确提问。

| 第一轮结果 | 向用户展示内容 | 向用户提出的问题 |
|-----------|--------------|----------------|
| 无真实错误 | 展示日志审查摘要："我已检查构建日志，未发现 ERROR/FAILED 等异常。" | "请您确认：在您这边的构建/运行过程中，是否也没有看到任何错误？如果有报错请贴出来。" |
| 发现错误 | 展示具体错误列表 | "以上是我在日志中发现的错误，请您确认这些是否完整？您那边是否还有其他报错？" |

用户回复的判定：

| 用户回复 | 判定 |
|---------|------|
| 明确回复"没有错误" / "确认无误" / "通过" | ✅ 第二轮通过 |
| 回复了新的错误信息 | ❌ 第二轮未通过 — 将新错误纳入修复流程 |
| 回复模糊（如"应该没问题吧"、"我没仔细看"） | ⚠️ **不算通过** — 追问用户要求明确确认，必要时请用户贴出实际日志截图 |
| 用户未回复 | ⏸️ 等待中 — 本项保持 ☐，禁止自行假设通过 |

**两轮交叉判定矩阵**

| 第一轮（AI 日志审查） | 第二轮（用户确认） | 最终判定 | 后续动作 |
|:---:|:---:|:---:|---------|
| ✅ 无错误 | ✅ 用户确认无错误 | ☑ **通过** | 标记该验证项完成 |
| ✅ 无错误 | ❌ 用户报告有错误 | ❌ **未通过** | AI 存在审查盲区，以用户反馈为准，进入错误修复流程 |
| ❌ 发现错误 | ✅ 用户确认仅此错误 | ❌ **未通过** | 按错误列表逐一修复，修复后重新执行双重交验 |
| ❌ 发现错误 | ❌ 用户补充更多错误 | ❌ **未通过** | 合并完整错误列表，逐一修复后重新执行双重交验 |

> 🔑 核心原则：**只有 ✅+✅ 才算通过**。AI 自检通过但用户未确认 ≠ 通过；用户说没问题但日志有 ERROR ≠ 通过（需向用户说明日志异常后再次确认）。
