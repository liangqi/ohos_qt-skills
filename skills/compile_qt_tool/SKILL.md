**警示信号**

当你发现自己有以下想法时，立即停止：

- 仅凭文档就下结论

- 假设其他平台的行为也适用于OHOS

- 没有阅读实际源代码

- "这应该和windows一样..." 
- "这个错误可能是....."
- "我觉得依赖可能是..."

**捕获到这些信号 → 停止。回去读代码。**

**遇到问题，优先查询 `compile_fix_pro.md`**

| 触发时机 | 执行动作 |
|---------|---------|
| 编译 / 链接 / 打包 / 运行出现任何错误 | **第一步**：在 `compile_fix_pro.md` 中搜索是否已有匹配的解决方案 |
| 找到匹配方案 | 直接按方案执行修复，不再重复分析 |
| 未找到匹配方案 | 按正常流程分析问题，修复后将新方案**追加写入** `compile_fix_pro.md` |

> ⚠️ 跳过知识库查询直接分析问题 = 违规。已解决过的问题不应浪费时间重新分析。

**平台分支必须显式隔离**

| 违规行为 | 正确做法 |
|---------|---------|
| 直接修改通用逻辑适配 OHOS | 用 `#if defined(Q_OS_OHOS)` / CMake `if(OHOS)` / qmake `ohos:` 条件隔离 |
| 改动导致 Linux/Windows/macOS 原逻辑不可用 | OHOS 改动必须封闭在条件分支内，不影响其他平台 |

**只改源头，不优先改生成物**

| 违规行为 | 正确做法 |
|---------|---------|
| 修改 build 目录下的 Makefile 或临时产物 | 优先改 CMakeLists.txt、.pro、源码、模板配置 |
| 把构建中间产物当交付件提交 | 所有改动必须追溯到源头文件 |

**修复成功必须沉淀**

| 触发时机 | 执行动作 |
|---------|---------|
| 任何编译 / 链接 / 打包 / 运行问题修复成功、| **必须**修复超过三个问题时必须先把之前修复的问题追加到 `compile_fix_pro.md`，包含：错误原文、发生阶段、根因、改动文件、验证命令 |

**门禁失败禁止标记成功**

| 检查项 | 未通过时 |
|-------|---------|
| 编译产物缺失 / HAP 未生成 | ❌ 不能写"完成" |
| 安装失败 / 启动失败 | ❌ 不能写"完成" |
| Qt .so 缺失 / RPATH 不完整 / 依赖断裂 | ❌ 不能写"完成" |

> 只有全部门禁通过，才能标记步骤完成。

**依赖先盘点，缺失不可猜**

| 违规行为 | 正确做法 |
|---------|---------|
| 假设某个 Qt 模块 / 三方库 / SDK 存在 | 在 `qt_env.md` 中明确记录每项依赖的状态（☑ 已就绪 / ☐ 缺失） |
| 跳过盘点直接编译 | 先完成 §3 依赖环境梳理，所有项状态明确后再进入编译 |

**平台能力限制要降级，不要硬绕**

| 违规行为 | 正确做法 |
|---------|---------|
| 对同一个平台限制反复重试同一命令 | 确认是平台限制后，记录限制原因，选择替代方案或功能降级 |
| 例：syscall / 权限 / 文件系统 / 动态库加载限制 | 记录到 `qt_env.md`，标注为「平台限制」并给出降级策略 |

**流程中的用户交互不可跳过**

| 违规行为 | 正确做法 |
|---------|---------|
| 流程写了「询问用户」「向用户提问」但没有实际提问就继续执行 | 必须真正向用户发出提问，**等到用户回复后**才能继续 |

### 3、依赖环境

**3.0 梳理当前项目的用途**

- 阅读项目的 README.md、官方文档或源码注释
- 明确项目的**核心功能**（例：代码编辑器组件、图表库、协议解析库）
- 明确项目的**目标产物类型**（动态库 / 静态库 / 可执行文件）
- 产出：一段 2-3 句话的项目摘要，追加到 `qt_env.md`

**3.1 Qt 版本依赖**

- 确认项目依赖的 Qt 大版本（Qt5 / Qt6）
  - 若为 Qt5，确认最低兼容的小版本号
  - 若为 Qt6，执行以下 **Qt5 兼容性评估流程**：

**Qt6 → Qt5 兼容性评估流程**

> 背景：当前鸿蒙化 Qt 分支仅支持 Qt5（5.12.12 / 5.15.16），若项目使用了 Qt6，需评估是否可适配 Qt5 版本。
>
> **重要原则**：适配时应使用 Qt 版本判断宏（`QT_VERSION_CHECK`）做条件编译，保持代码对 Qt5 和 Qt6 的兼容性，而非直接删除 Qt6 代码。

**Step A：检测是否使用了 Qt6 独有特性**

在源码和构建文件中搜索以下 Qt6 特征，任一命中即判定为"使用了 Qt6 独有特性"：

| 检测项 | 搜索方式 |
|--------|---------|
| Qt6 专属模块 | grep 构建文件中的 `Qt6::` / `find_package(Qt6` / `QT += core5compat` |
| Qt6 CMake API | grep `qt_add_qml_module` / `qt_add_executable` / `qt_add_resources` |
| Qt6 独有头文件/类 | grep `#include <QPromise>` / `QFuture::then` / `QStringView` 的 Qt6 新 API |
| QML 变更 | grep `import QtQuick` (无版本号写法为 Qt6 风格) |
| C++17 强依赖 | 结合 `CMAKE_CXX_STANDARD 17` 和 Qt6 API 同时出现 |

- 若**未命中**任何 Qt6 独有特性 → 项目本身兼容 Qt5，直接按 Qt5 流程继续
- 若**命中** → 进入 Step B

**Step B：查找仓库中的 Qt5 版本**

> 很多项目的 Qt5 版本**名字里不含 `qt5`**（如 `v1.0.0`、`master`），**不能仅靠名字 grep**，必须检查构建文件内容。

```bash
# 1. 名称快速筛选
git branch -a | grep -iE 'qt5|5\.[0-9]+'
git tag -l | grep -iE 'qt5|5\.[0-9]+'

# 2. 列出全部 tag 和分支（不可跳过）
git tag -l --sort=-creatordate
git branch -a

# 3. 对每个 tag/分支，用 git show 检查构建文件是否引用 Qt5（免切换）
git show <ref>:CMakeLists.txt 2>/dev/null | grep -iE 'find_package\(Qt5|Qt5::'
git show <ref>:<项目名>.pro 2>/dev/null | grep -iE 'QT\s*\+='
```

**判定规则**：构建文件含 `find_package(Qt5` / `Qt5::` → Qt5 兼容；仅含 `find_package(Qt6` 且无 Qt5 回退 → Qt6 不兼容。每个 tag/分支的检查结果记入 `qt_env.md`。

- 若**找到** Qt5 兼容版本 → 按以下优先级选取后进入 Step C
- 若**全部遍历后均未找到** → 记录到 `qt_env.md`："仓库无 Qt5 版本（已检查全部 N 个 tag 和 M 个分支），需手动适配"，**向用户报告并等待决策**

**选取优先级**（tag 和分支同时存在时）：

> **tag 优先于分支**。

| 优先级 | 类型 | 理由 |
|:---:|------|------|
| 1️⃣ | **tag**（如 `v1.2.3`、`qt5-stable`） | 不可变快照，版本语义明确，可复现性最强 |
| 2️⃣ | **release 分支**（如 `release/1.x`、`stable`） | 虽可变但通常受保护，稳定性较高 |
| 3️⃣ | **普通分支**（如 `qt5`、`support-qt5`） | 可能仍在变动，需额外验证稳定性 |

- 若同一版本既有 tag 又有分支 → **使用 tag**
- 若有多个候选 tag → 选取版本号最高或日期最新的

**Step C：判定候选版本是否为正式版本**

> 不能盲目采纳找到的分支/tag，必须验证其为作者正式发布的版本。

逐项检查以下判定标准：

| 序号 | 判定标准 | 判定为正式版本 | 判定为调试/实验性 |
|:---:|---------|:---:|:---:|
| 1 | 分支/tag 命名 | `release-*`、`stable-*`、`v1.2.3`、`qt5`、`master` 等规范命名 | `test-*`、`wip-*`、`dev-xxx`、`fix-*`、含个人名等临时命名 |
| 2 | 提交历史 | 有持续的提交记录（非单次提交后废弃） | 仅 1-2 次提交后长期无更新 |
| 3 | README / CHANGELOG | 有对应版本的发布说明或文档 | 无任何说明或标注为"experimental" |
| 4 | CI/CD 状态 | 有构建通过的标记或 Release 包 | 无构建记录 |
| 5 | 与主分支的关系 | 从主分支分叉或被主分支合并过 | 孤立分支，与主线无交集 |

**判定规则**：
- 满足 ≥3 项"正式版本"标准 → ✅ **采纳**，切换到该分支/tag 继续流程
- 满足 ＜3 项 → ❌ **不采纳**，视为调试分支

**最终结论记录到 `qt_env.md`**：

| 结论 | 后续动作 |
|------|---------|
| ✅ 找到可用的 Qt5 正式版本 | 记录分支/tag 名称，**进入 Step D 执行切换与依赖重新评估** |
| ❌ 找到分支/tag 但判定为非正式版本 | 在qt_env.md中记录判定依据（哪几项不满足），**向用户报告：仓库存在 Qt5 分支但非正式版本，不建议采用，需手动适配** |
| ❌ 仓库无任何 Qt5 版本 | 在qt_env.md中记录结论，**向用户报告：需在 Qt6 代码基础上手动适配 Qt5 API，工作量较大** |

**Step D：切换到目标版本并重新评估依赖环境**

> 前提：Step C 判定为 ✅ 后方可进入。

1. **执行切换**：`git checkout <选定的tag或分支>` → 用 `git log --oneline -1` 确认 HEAD 正确
2. **验证切换成功**：确认构建文件存在且引用 Qt5（无 `Qt6::` / `find_package(Qt6`）
   - 通过 → 在 `qt_env.md` 记录 tag/分支名、commit hash、切换时间
   - 未通过 → **向用户报告并等待决策**
3. **重新执行 §3.0～§3.6**：切换后代码已变，之前基于 Qt6 梳理的依赖信息失效，必须基于新代码**全量重跑**依赖梳理
4. **记录结论**到 `qt_env.md`：切换后版本、Qt5 匹配性（☑/☐）、依赖可满足性、整体评估（可直接编译 / 需少量适配 / 需大量适配）



**Qt 版本适配原则（重要！）**

> 当需要同时支持 Qt5 和 Qt6 时，应使用 Qt 版本判断宏做条件编译，而非直接修改代码只支持单一版本。

**版本判断宏使用示例**：

```cpp
// 方式一：使用 QT_VERSION_CHECK 宏
#if QT_VERSION >= QT_VERSION_CHECK(6, 0, 0)
    // Qt6 代码路径（保持原样，不做修改）
    QPromise<int> promise;  // Qt6 原有 API
#else
    // Qt5 替代实现（新增，仅鸿蒙编译时使用）
    QFuture<int> future = QtConcurrent::run([]() { return 42; });
#endif

// 方式二：使用 QT_VERSION_MAJOR（Qt6 新增）
#if QT_VERSION_MAJOR >= 6
    // Qt6 代码
#else
    // Qt5 代码
#endif

// 方式三：CMake 中判断
find_package(QT NAMES Qt6 Qt5 REQUIRED COMPONENTS Core)
if(QT_VERSION_MAJOR EQUAL 6)
    # Qt6 特定配置
else()
    # Qt5 特定配置
endif()
```

**适配原则**：
| 原则 | 说明 |
|------|------|
| **不影响 Qt6 原有代码** | Qt6 代码路径保持原样，不做任何修改 |
| **只为 Qt5 添加分支** | 在 `#else` 或 `#if QT_VERSION < ...` 中添加 Qt5 替代实现 |
| **Qt6 不需要测试** | 鸿蒙仅支持 Qt5，Qt6 版本无需在鸿蒙环境验证 |
| **仅测试 Qt5 鸿蒙版** | 确保添加的 Qt5 分支在鸿蒙上正常工作 |

> **核心目标**：鸿蒙适配 Qt5 时，保持 Qt6 原有代码完全不变，确保项目在其他平台（Windows/Linux/macOS）上仍可使用 Qt6 正常编译运行。

**🔐 双重交验协议（适用于「编译构建无错误」与「HAP 安装启动无错误」）**

> 每个验证项必须独立完成两轮验证，任一轮未通过即判定该项 ❌。禁止合并两项、禁止跳过任何一轮。

**第一轮：AI 自动审查（日志审查）**

| 步骤 | 执行动作 | 判定标准 |
|:---:|---------|---------|
| 1 | 获取完整构建/安装日志（不截断） | 日志成功获取 |
| 2 | 在日志中搜索以下**失败关键词**：`ERROR`、`FAILED`、`fatal`、`undefined reference`、`cannot find`、`No such file`、`BUILD FAILED`、`Install Failed`、`crash`、`SIGSEGV`、`SIGABRT` | 逐一记录命中项 |
| 3 | 对每个命中项进行**误报排除**：是否属于注释/文档描述中的文字、是否为已忽略的已知警告、是否为依赖库内部日志但不影响产物 | 仅保留真实错误 |
| 4 | 输出第一轮审查结论 | 「无真实错误」或「发现 N 个错误：\<列表\>」 |

> ⚠️ 搜索关键词必须**逐个执行**，不得仅凭"看了一眼日志没发现问题"就跳过。每个关键词的搜索结果（命中数或零命中）需可追溯。

**第二轮：用户确认（人工交验）**

> 第一轮完成后（无论结果如何），必须将审查结论**完整展示**给用户，并明确提问。

| 第一轮结果 | 向用户展示内容 | 向用户提出的问题 |
|-----------|--------------|----------------|
| 无真实错误 | 展示日志审查摘要："我已检查构建日志，未发现 ERROR/FAILED 等异常。" | "请您确认：在您这边的构建/运行过程中，是否也没有看到任何错误？如果有报错请贴出来。" |
| 发现错误 | 展示具体错误列表 | "以上是我在日志中发现的错误，请您确认这些是否完整？您那边是否还有其他报错？" |

用户回复的判定：

| 用户回复 | 判定 |
|---------|------|
| 明确回复"没有错误" / "确认无误" / "通过" | ✅ 第二轮通过 |
| 回复了新的错误信息 | ❌ 第二轮未通过 — 将新错误纳入修复流程 |
| 回复模糊（如"应该没问题吧"、"我没仔细看"） | ⚠️ **不算通过** — 追问用户要求明确确认，必要时请用户贴出实际日志截图 |
| 用户未回复 | ⏸️ 等待中 — 本项保持 ☐，禁止自行假设通过 |

**两轮交叉判定矩阵**

| 第一轮（AI 日志审查） | 第二轮（用户确认） | 最终判定 | 后续动作 |
|:---:|:---:|:---:|---------|
| ✅ 无错误 | ✅ 用户确认无错误 | ☑ **通过** | 标记该验证项完成 |
| ✅ 无错误 | ❌ 用户报告有错误 | ❌ **未通过** | AI 存在审查盲区，以用户反馈为准，进入错误修复流程 |
| ❌ 发现错误 | ✅ 用户确认仅此错误 | ❌ **未通过** | 按错误列表逐一修复，修复后重新执行双重交验 |
| ❌ 发现错误 | ❌ 用户补充更多错误 | ❌ **未通过** | 合并完整错误列表，逐一修复后重新执行双重交验 |

> 🔑 核心原则：**只有 ✅+✅ 才算通过**。AI 自检通过但用户未确认 ≠ 通过；用户说没问题但日志有 ERROR ≠ 通过（需向用户说明日志异常后再次确认）。
