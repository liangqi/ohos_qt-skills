### 3、依赖环境

**3.0 梳理当前项目的用途**

- 阅读项目的 README.md、官方文档或源码注释
- 明确项目的**核心功能**（例：代码编辑器组件、图表库、协议解析库）
- 明确项目的**目标产物类型**（动态库 / 静态库 / 可执行文件）
- 产出：一段 2-3 句话的项目摘要，追加到 `qt_env.md`

**3.1 Qt 版本依赖**

- 确认项目依赖的 Qt 大版本（Qt5 / Qt6）
  - 若为 Qt5，确认最低兼容的小版本号
  - 若为 Qt6，执行以下降级评估流程：

**Qt6 → Qt5 降级评估流程**

> 背景：当前鸿蒙化 Qt 分支仅支持 Qt5（5.12.12 / 5.15.16），若项目使用了 Qt6，需评估是否可降级到 Qt5 版本。

**Step A：检测是否使用了 Qt6 独有特性**

在源码和构建文件中搜索以下 Qt6 特征，任一命中即判定为"使用了 Qt6 独有特性"：

| 检测项 | 搜索方式 |
|--------|---------|
| Qt6 专属模块 | grep 构建文件中的 `Qt6::` / `find_package(Qt6` / `QT += core5compat` |
| Qt6 CMake API | grep `qt_add_qml_module` / `qt_add_executable` / `qt_add_resources` |
| Qt6 独有头文件/类 | grep `#include <QPromise>` / `QFuture::then` / `QStringView` 的 Qt6 新 API |
| QML 变更 | grep `import QtQuick` (无版本号写法为 Qt6 风格) |
| C++17 强依赖 | 结合 `CMAKE_CXX_STANDARD 17` 和 Qt6 API 同时出现 |

- 若**未命中**任何 Qt6 独有特性 → 项目本身兼容 Qt5，直接按 Qt5 流程继续
- 若**命中** → 进入 Step B

**Step B：查找仓库中的 Qt5 版本**

在当前仓库中查找可能的 Qt5 兼容版本：

```bash
# 查找含 qt5 / Qt5 / 5.x 的分支
git branch -a | grep -iE 'qt5|5\.[0-9]+'

# 查找含 qt5 / Qt5 / 5.x 的 tag
git tag -l | grep -iE 'qt5|5\.[0-9]+'

# 如果没有明确命名，查看所有 tag 的时间和描述
git tag -l --sort=-creatordate | head -20
```

- 若**未找到**任何 Qt5 分支或 tag → 记录到 `qt_env.md`："仓库无 Qt5 版本，需手动适配降级"，**向用户报告并等待决策**
- 若**找到**候选分支/tag → 按以下优先级选取后进入 Step C

**选取优先级**（tag 和分支同时存在时）：

> tag 是不可变的版本快照，代表作者在某个时间点明确标记的发布状态；分支则可能持续变动。因此 **tag 优先于分支**。

| 优先级 | 类型 | 理由 |
|:---:|------|------|
| 1️⃣ | **tag**（如 `v1.2.3`、`qt5-stable`） | 不可变快照，版本语义明确，可复现性最强 |
| 2️⃣ | **release 分支**（如 `release/1.x`、`stable`） | 虽可变但通常受保护，稳定性较高 |
| 3️⃣ | **普通分支**（如 `qt5`、`support-qt5`） | 可能仍在变动，需额外验证稳定性 |

- 若同一版本既有 tag 又有分支 → **使用 tag**
- 若有多个候选 tag → 选取版本号最高或日期最新的

**Step C：判定候选版本是否为正式版本**

> ⚠️ 不能盲目采纳找到的分支/tag，必须验证其为作者正式发布的版本。

逐项检查以下判定标准：

| 序号 | 判定标准 | 判定为正式版本 | 判定为调试/实验性 |
|:---:|---------|:---:|:---:|
| 1 | 分支/tag 命名 | `release-*`、`stable-*`、`v1.2.3`、`qt5`、`master` 等规范命名 | `test-*`、`wip-*`、`dev-xxx`、`fix-*`、含个人名等临时命名 |
| 2 | 提交历史 | 有持续的提交记录（非单次提交后废弃） | 仅 1-2 次提交后长期无更新 |
| 3 | README / CHANGELOG | 有对应版本的发布说明或文档 | 无任何说明或标注为"experimental" |
| 4 | CI/CD 状态 | 有构建通过的标记或 Release 包 | 无构建记录 |
| 5 | 与主分支的关系 | 从主分支分叉或被主分支合并过 | 孤立分支，与主线无交集 |

**判定规则**：
- 满足 ≥3 项"正式版本"标准 → ✅ **采纳**，切换到该分支/tag 继续流程
- 满足 ＜3 项 → ❌ **不采纳**，视为调试分支

**最终结论记录到 `qt_env.md`**：

| 结论 | 后续动作 |
|------|---------|
| ✅ 找到可用的 Qt5 正式版本 | 记录分支/tag 名称，切换后重新从 §3.2 开始梳理模块依赖 |
| ❌ 找到分支/tag 但判定为非正式版本 | 在qt_env.md中记录判定依据（哪几项不满足），**向用户报告：仓库存在 Qt5 分支但非正式版本，不建议采用，需手动适配** |
| ❌ 仓库无任何 Qt5 版本 | 在qt_env.md中记录结论，**向用户报告：需在 Qt6 代码基础上手动降级适配 Qt5 API，工作量较大** |

**3.2 Qt 模块依赖**

- 逐一梳理项目实际引用了哪些 Qt 模块
  - 核心模块：QtCore、QtGui、QtWidgets、QtNetwork 等
  - 扩展模块：QtMultimedia、QtWebEngine、QtBluetooth 等
  - 确认每个模块在鸿蒙化分支中是否已移植

**梳理方法（按优先级）**：
1. 分析 CMakeLists.txt 中的 `find_package(Qt...)` / `target_link_libraries(Qt...)`
2. 分析 .pro 文件中的 `QT +=` 行
3. grep 源码中的 `#include <QXxx>` 头文件，反推所属模块
4. 若以上信息不一致，以构建文件（CMakeLists.txt / .pro）为准

**输出格式**：

| Qt 模块 | 引用证据 | 鸿蒙分支状态 | 备注 |
|---------|---------|:----------:|------|
| QtCore | `find_package(Qt5 COMPONENTS Core)` | ☑ 已移植 | — |
| QtWidgets | `#include <QWidget>` | ☑ 已移植 | — |
| QtPrintSupport | `QT += printsupport` | ☐ 未移植 | 需降级处理 |

**3.3 系统能力直调**

- 确认项目是否绕过 Qt 直接调用了操作系统 API
  - 若存在，评估在 OHOS 上的替代方案

**3.4 三方库依赖**

- 梳理除 Qt 仓库本身之外的所有三方库依赖
  - 记录库名、功能、作用、版本、引入方式（源码编译 / 预编译包 / 系统安装）
  - 确认各三方库是否支持 OHOS 交叉编译

**3.5 构建系统与编译配置**

- 梳理项目的构建系统类型（qmake / CMake / 混合）
- 梳理编译选项、宏定义、条件编译分支
- 确认是否存在平台相关的构建脚本或工具链文件
- 列出详细的依赖项

**3.6 环境就绪比对**

- 盘点当前已具备的编译环境（工具链、SDK、已编译产物等）
- 将已具备的环境与 3.1～3.5 梳理出的依赖项逐一比对
  - **已就绪**：标记为 ☑
  - **不确定**：向用户提问确认，明确列出需要确认的具体项
  - **缺失**：标记为 ☐，记录缺失原因

**追加至 `qt_env.md`**

将 3.1～3.6 的梳理结果按以下表格形式追加到 `qt_env.md` 中，作为依赖全景记录：

| 类别 | 依赖项 | 状态 | 来源/路径 | 备注 |
|------|--------|:---:|---------|------|
| Qt 模块 | QtCore | ☑ | `<产物路径>/lib/libQt5Core.so` | — |
| Qt 模块 | QtPrintSupport | ☐ | — | 鸿蒙分支未移植，需降级 |
| 三方库 | zlib | ☑ | 系统自带 | — |
| 工具链 | OHOS NDK | ☑ | `<SDK路径>` | — |

### 4、计划协同
**4.1 知识库准备**

- 询问用户是否已有 `compile_fix_pro.md`（问题解决集合知识库）
  - **已有** — 记录其路径到 `qt_compile_plan.md` 中
  - **没有** — 询问用户创建路径，创建 `compile_fix_pro.md` 并写入示例格式：

    ```
    ## 问题标题
    - 问题描述：具体的错误信息
    - 发生环节：编译 / 链接 / 打包 / 运行
    - 产生原因：根因分析
    - 修复方案：具体的修复步骤与代码改动
    ```

**4.2 编译前准备**

**前置条件**：§3 的 `qt_env.md` 中所有必要依赖状态为 ☑ 或已标注降级方案（⚠️）

**执行步骤**：
1. 查看 `qt_env.md`，确认所有依赖状态明确 — 若有 ☐ 项，先解决或标注降级方案
2. 调用 `create-qt-app` skill 创建/配置工程结构
   - create-qt-app 会检测 `qt_env.md` 进入快速模式
3. 如果调用 create-qt-app 遇到错误：
   1. 按铁律先查 `compile_fix_pro.md` 是否有已知方案
   2. 识别错误产生在哪个环节（预处理 / 编译 / 链接 / 打包）
   3. 尝试修复
      - 修复成功 — 将问题及解决方案按照示例格式记入 `compile_fix_pro.md`
      - 修复失败 — 向用户求助，提供错误信息、已尝试的方案和需要的协助
4. 在当前目录创建 `qt_compile_plan.md`，整理详细的编译步骤与计划
5. **将 `qt_compile_plan.md` 展示给用户确认后，方可进入 §4.3**

**4.3 参照 `qt_compile_plan.md` 执行调用 build-run-qt-app 编译**

- 按照计划逐步执行编译
- 如果编译遇到错误：
  1. 按铁律先查 `compile_fix_pro.md` 是否有已知方案
  2. 识别错误产生在哪个环节（预处理 / 编译 / 链接 / 打包）
  3. 分析错误发生的原因
  4. 尝试修复
     - 修复成功 — 将问题及解决方案按照示例格式记入 `compile_fix_pro.md`
     - 修复失败 — 向用户求助，提供错误信息、已尝试的方案和需要的协助

**错误重试策略**：
- 同一错误最多尝试修复 **3 次**
- 每次修复尝试必须使用**不同方案**（禁止重复同一修复方式）
- 超过 3 次 → 停止修复，整理完整的错误上下文和已尝试方案，向用户求助
