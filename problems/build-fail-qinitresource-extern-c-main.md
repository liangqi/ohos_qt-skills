# The linkage conflict between Q_INIT_RESOURCE and extern "C" main

## Error message

```
ld.lld: error: undefined symbol: qInitResources_tcpview
>>> referenced by main.cpp:17 (.../OhosExampleApp/main.cpp:17)
>>>               CMakeFiles/OhosTcpView.dir/main.cpp.o:(main)
>>> did you mean to declare qInitResources_tcpview() as extern "C"?
>>> defined in: CMakeFiles/OhosTcpView.dir/OhosTcpView_autogen/.../qrc_tcpview.cpp.o
clang++: error: linker command failed with exit code 1
```

## Scenario

The standard form of a Qt OHOS application entry shim (scenario two, copied from the Qt template) is `extern "C" int main(int argc, char*argv[])`,
which guarantees `main` appears in the dynamic symbol table with C linkage so the Qt OHOS glue's `dlsym("main")` can find it. If that main calls
`Q_INIT_RESOURCE(name)` — common in an application's original main.cpp, to register .qrc resources — the link stage reports the undefined symbol above.

## Cause

The `Q_INIT_RESOURCE(name)` macro expands to include the declaration `extern int qInitResources_##name();`. When that declaration sits inside
`extern "C" int main() { ... }`, it inherits C language linkage (an unmangled bare name), so main.o references the bare name
`qInitResources_<name>`; meanwhile, the `qrc_<name>.cpp` generated by rcc defines that function with C++ linkage (mangled). lld can't find
the bare name → undefined symbol, with the hint "did you mean to declare ... as extern C?".

## Solution

**Preferred: omit Q_INIT_RESOURCE.** In a shared library (an OHOS Qt app is a .so), the `qrc_<name>.cpp` generated by rcc contains a
namespace-scope static initializer calling `qRegisterResourceData(...)`, which registers the resources automatically when the .so loads (its .o
is already on the link line). Q_INIT_RESOURCE exists only to force resources to be pulled in from a static archive (the "the only reference is
Q_INIT_RESOURCE" case), and is redundant in a shared library. Deleting `Q_INIT_RESOURCE(name);` from the extern "C" main fixes the link error,
and the resources are still registered.

```cpp
// OhosExampleApp/main.cpp — delete Q_INIT_RESOURCE(tcpview);
extern "C" int main(int argc, char *argv[]) {
#if QT_VERSION < QT_VERSION_CHECK(6, 0, 0)
    QCoreApplication::setAttribute(Qt::AA_EnableHighDpiScaling);
#endif
    // Q_INIT_RESOURCE(tcpview);  // omitted: the .so registers automatically, and this avoids the extern "C" main linkage conflict
    QApplication app(argc, argv);
    ...
}
```

**Second choice** (when you need explicit registration): move Q_INIT_RESOURCE into a C++-linkage helper (not extern "C") and call it from main:
```cpp
static void initResources() { Q_INIT_RESOURCE(name); }   // C++ linkage, matching rcc's definition
extern "C" int main(...) { initResources(); ... }
```

## Notes

- Before deleting it, confirm `qrc_<name>.cpp.o` really is on the link line (CMake AUTORCC ON + the .qrc in the target sources is enough).
  Without `--gc-sections` on the link, the static initializer won't be stripped.
- In the original Linux build, main is an ordinary C++ `int main` (not extern "C"), so Q_INIT_RESOURCE and rcc both have C++ linkage and
  don't conflict — which is why this problem only appears on OHOS (with the extern "C" main shim).
- If icons/translations are missing at runtime, fall back to the second option (the helper).
- How to tell resources are still registered: the .so links qrc_<name>.cpp.o and there's no --gc-sections → the static initializer runs → resources are registered.
