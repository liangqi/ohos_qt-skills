# Common pitfalls in HarmonyOS cross-compilation and on-device builds

This page collects only platform-level patterns reproduced across two or more frameworks. Framework-specific fixes still belong in the corresponding domain knowledge base.

## A Rust target cfg is not a product-level platform classification

The common OHOS Rust target is `aarch64-unknown-linux-ohos`, where `target_os = "linux"` and `target_env = "ohos"`. Therefore:

- Keying only on `target_os = "linux"` or a framework's `desktop` cfg may wrongly enable desktop plugins and system integrations.
- Treating only Android as "mobile" makes OHOS fall into the wrong branch for things like the filesystem.
- `cfg(mobile)` is a condition injected by the framework/build configuration; `target_os` and `target_env` are Rust target attributes. They are not interchangeable.

A typical correction:

```rust
#[cfg(all(desktop, not(target_env = "ohos")))]
fn desktop_only() {}

#[cfg(any(target_os = "android", target_env = "ohos"))]
fn mobile_platform_path() {}
```

Before making corrections, check the target crate's cfg definitions and their intended semantics — don't mechanically replace every `linux` or `android` branch.

## `c_char` signedness must come from the target ABI

On the verified OHOS Rust target, `std::os::raw::c_char` is `u8`; on many Unix targets it is `i8`. C bindings that hard-code `*mut i8` / `*const i8` can produce `E0308` type mismatches on OHOS.

Handling principles:

1. In your own FFI, use `std::os::raw::c_char` or the corresponding libc type — don't hard-code signedness.
2. For non-essential indirect dependencies, disable the whole dependency chain under an OHOS cfg.
3. When a core dependency needs a fork/patch, keep the fix confined to the ABI type boundary and add cross-compilation verification.

Historically, `git2`'s filter paths and some `nix` structures triggered this class of problem; whether a specific version is still affected should be re-checked against the source.

## System-level permissions depend on the right signing profile

Runtimes that need JIT or executable memory (a JVM, for example) may request `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY`. An ordinary debug profile generated by hand with `hap-sign-tool.jar` doesn't necessarily include the system-level permission ACL; generate a properly authorized profile through your team's approved DevEco/devecocli signing process.

Verification must not stop at "installed successfully": also check the permission grant result, process startup, and crash logs. For toolchain operating rules, see [[deveco-cli-usage-rules]].

## A working tree that builds is not proof of reproducibility

Cargo/npm caches, untracked files, and locally generated directories can mask a missing commit or a wrong path. Before releasing or archiving, do at least one pass of:

1. Clone into a fresh temporary directory.
2. Run the full build chain from scratch following the SETUP/build entry point.
3. Confirm the build doesn't depend on caches or uncommitted files from the original working tree.
4. Check whether the generated project is accidentally excluded by an upstream `.gitignore` (e.g. `/gen/`).
5. After verification, confirm the temporary clone has no unexpected modifications.

If you must commit `gen/ohos/`, use the narrowest possible `.gitignore` negation rule and keep excluding artifacts such as `.hvigor/`, `build/`, and `oh_modules/`.

## Applicability boundaries

- The cfg and `c_char` conclusions apply to a specific OHOS toolchain; re-confirm after upgrading Rust/the NDK.
- Signing capabilities depend on the device, certificate type, and permission policy — don't treat a profile that worked once as a reusable credential.
- Fresh-clone is a reproducibility gate; it does not replace on-device functional verification.
