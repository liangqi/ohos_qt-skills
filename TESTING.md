# Testing and verification

"Testing" in this repository has three levels: **gates (automatic) → smoke (semi-automatic) → real-device end-to-end (human-driven + gate verdict)**.
If any level hasn't been run, you can't say "this version is usable".

---

## 1. Automated gates (must run on every commit)

```bash
python _scripts/verify.py                   # contract / structure / references / indexes / release manifest / hygiene (10 kinds of check)
python -m unittest discover -s tests -v     # consistency + engine + scan (156 cases)
python tools/faults-build.py check          # fault library source of truth ↔ derived artifacts (error must be 0)
```

(`bash _scripts/verify.sh` is a thin bash wrapper around the same checks; on Windows use the `python` form directly.)

One command runs all four (CI uses this; the exit code is the verdict):

```bash
python _scripts/ci.py       # pure Python, runs on Windows without bash too
bash _scripts/ci.sh         # equivalent thin wrapper
```

On Windows without bash, use `python _scripts/verify.py` to run the first one equivalently.

## 3. Offline end-to-end (no device needed, already run successfully on this machine)

Before installing the HarmonyOS toolchain, first prove that "the execution layer itself isn't broken": take a synthetic Qt project and run
`scan → plan → status → patch → verify → analyze-log`. Only once this chain works does going onto a real device make sense;
if it doesn't, the first step on Windows will get stuck on the tools rather than on HarmonyOS.

**No step of this chain needs the SDK or a device** (`verify` will honestly report G0 FAIL, which is the correct behavior).

| Step | Command (`--project` points at the sample project) | Expected output (measured 2026-11-02) |
|------|----------------------------------------------------|----------------------------------------|
| 1. Scan | `qt-ohos-run.py --project <project> scan` | `build system: cmake \| qt: 5 (find_package(Qt5)) \| modules: core, gui, network, widgets \| sources: N`, followed by a `Qt HarmonyOS Porting Risk Report` listing risks grouped by level (R009 `qprocess_usage`, R012 `system_tray_usage`, etc., with `file:line`). When the Qt major version can't be determined, this shows `qt: undetermined` and prints a WARNING |
| 2. Plan | `qt-ohos-run.py --project <project> plan` | `plan: 6 steps (auto=1 assisted=3 manual=2)`, with S001…S006 each marked auto/assisted/manual |
| 3. Status | `qt-ohos-run.py --project <project> status` | Four lines: `stage: plan` / `next: {"action": "patch"}` / `completed:` / `remaining:` |
| 4. Auto-fix | `qt-ohos-run.py --project <project> patch` | `no automatic fixes applicable` (no hits) or `applied N fixes`, with all changes recorded in `.qt-ohos/changes.json` |
| 5. Gates | `qt-ohos-run.py --project <project> verify` | `G0 Environment FAIL missing: qt_sdk_prefix or build_command`, G1 FAIL (no build files/plan without a scan), G2 NOT_RUN (without a risk_scan you can't say "no critical risks"), G3–G12 NOT_RUN, `Result: FAIL` — the correct verdict with no SDK configured and no scan |
| 6. Log diagnosis | `qt-ohos-run.py analyze-log <log>` | `Hits:` lists matching patterns with confidence, `Top hit: QOH001 (qpa_plugin_not_found)`, followed by cause / diagnose / fix / read |
| 7. Manifest reconciliation | `python _scripts/gen-manifest.py --check` | `gen-manifest: counts consistent (135 pages / 156 cases)…`; on ordinary commits the digest shows as an "old snapshot"; before a release refresh it with the same script, then run `--check --strict` |

Step 6 is the easiest to verify: put a line `dlopen failed: library "libqohos.so" not found` into a log;
it should hit QOH001, and following `read:` should open the corresponding `problems/` page.

**Three known pitfalls (fixed this time)**:

- `scan <path>` writes state into the **target project's** `.qt-ohos/`, while `plan`/`patch` read the **current directory** by default.
  Running `scan ~/app` from the repository root and then `plan` reports "no migration state". Use
  `--project <project>` consistently (or run inside the project directory); the hint now gives this usage directly;
- `scan`'s positional argument used to be required and clashed with `--project`'s dest, so `--project X scan` made
  argparse error out — the two forms (`scan <dir>` / `--project <dir> scan`) are now equivalent;
- `analyze-log` is pure log analysis and needs no project state; it used to print a misleading "run `init` first" line first,
  and now it only tries to write back when `--project` is passed explicitly.

## 4. Windows end-to-end testing (pending)

Goal: on a **clean environment**, run the complete chain with a **Qt application that has never appeared in this repository before**,
proving that `trunk` is more than a documentation makeover.

### 0. Environment preparation (one-time)

| Item | Requirement | Check command |
|------|-------------|---------------|
| OS | Windows 10/11 x64 | `winver` |
| Python | 3.10+ | `python --version` |
| Git | Any recent version | `git --version` |
| DevEco Studio | With the HarmonyOS SDK (API 12+) | DevEco → SDK Manager |
| hdc | Comes with the SDK; can connect to a real device/emulator | `hdc list targets` |
| Qt OHOS SDK | 5.15 (recommended) or 5.12 | Built with `qt-sdk-run.py` or reuse an existing one |
| Disk | ≥ 30 GB (Qt source + build artifacts) | — |

### 0.1 Windows-specific pre-check (getting this wrong wastes hours)

```powershell
python --version                             # 3.10+
git config --global core.longpaths true      # tdesktop's path depth exceeds 260 characters
# Projects with submodules (tdesktop's Qt configuration lives in a cmake submodule) must be cloned recursively:
git clone --recursive <url> <dir>
```

- The gates don't need bash: use `python _scripts/ci.py` (`ci.sh` is just its thin wrapper).
- Project paths may contain spaces and Chinese characters; `--project "C:\Users\张三\我的 项目"` works directly.
- When the Qt major version can't be determined (the Qt configuration is in a submodule that wasn't fetched), first `config set qt_version 6`, then scan;
  otherwise it will be assessed against the 5.15 module matrix.

### 1. Get the code and run the gates first (works without installing the environment)

```powershell
git clone -b trunk https://gitcode.com/OpenHarmonyPCDeveloper/ohos_qt-skills.git
cd ohos_qt-skills
python _scripts/ci.py                       # expect "CI: all passed" (156 cases)
python _scripts/verify.py                   # expect PASS (0 error / 0 warning)
python tools/faults-build.py check          # expect error=0
```

> This step alone verifies that "the repository itself is healthy", regardless of whether the HarmonyOS toolchain is installed.

### 2. Initialize the environment and generate `ENV.local.md`

```powershell
python tools/qt-sdk-run.py init             # or just say "initialize" in the agent
# Edit ENV.local.md and fill in at least: DEVECO_CLI / OHOS_SDK_NATIVE / QT5_15_OHOS_SDK
python tools/qt-sdk-run.py envcheck         # or the pre-checks of qt-ohos-run.py verify
```

### 3. Pick an application and assess feasibility (step 0, not skippable)

Pick a medium-sized **Qt Widgets + a few third-party libraries** application (avoid Qt WebEngine / Qt6-only / heavy D-Bus),
such as a desktop tool depending on SQLite, zlib, and libpng.

```powershell
python portgraph/portgraph.py ingest all            # first time, needs a network connection
python portgraph/portgraph.py scan <application path>
python portgraph/portgraph.py analyze <app> --summary
python portgraph/portgraph.py deps <app>
python portgraph/portgraph.py fetch-deps <app> --dry-run
```

Record: **the three-state verdict, blockers, and unknowns (dependencies that need building from source)**. If the verdict is `blocked` and the blockers
are hard blockers (Qt WebEngine, a required D-Bus service, etc.), switch applications — that itself is a validation of the assessment capability.

#### What to expect when trying a heavy Qt6 project like tdesktop (measured on this machine 2026-11-02)

| Metric | Measured value | Meaning |
|--------|----------------|---------|
| Repository size | 6920 files / 3298 C/C++ sources | `scan` takes 12.3 seconds on macOS; Windows will be somewhat slower |
| Qt major version | Needs Qt6 (`find_package(QT NAMES Qt6 …)` takes precedence) | With only a Qt5 OHOS SDK it **breaks at the Qt version prerequisite**; don't rush to chase other errors |
| Version detection | The configuration is in a `cmake` submodule | A non-recursive clone shows `qt: undetermined` and assesses against 5.15 (conservative); `config set qt_version 6` corrects it |
| Three-state verdict | `UNCERTAIN` | Not `blocked`: on the module matrix, Qt6 core/gui/network/widgets are available |
| Third-party | ffmpeg, openssl, zlib caught at code level; `portgraph deps` additionally reports rnnoise, tde2e, wallet_engine needing cross-compilation from source | These are the main workload of this project |
| Platform-bound code | 161 critical (mostly `win32_api`) | These are Windows-specific implementations that must be rewritten against OHOS APIs when porting, not "change a macro" |
| Realistic goal | Get `scan → assess → plan` working, then pick **one** library (such as `lib_tl` or `lib_base`) and build a `.so` | Getting the whole package onto a real device isn't realistic; don't mistake "can't finish" for the tools being broken |

### 4. Run the migration pipeline

```powershell
python tools/qt-ohos-run.py --project <project dir> init
python tools/qt-ohos-run.py --project <project dir> scan
python tools/qt-ohos-run.py --project <project dir> plan
python tools/qt-ohos-run.py --project <project dir> patch
python tools/qt-ohos-run.py --project <project dir> build
python tools/qt-ohos-run.py --project <project dir> package
python tools/qt-ohos-run.py --project <project dir> install
python tools/qt-ohos-run.py --project <project dir> launch
python tools/qt-ohos-run.py --project <project dir> smoke
python tools/qt-ohos-run.py --project <project dir> verify   # ← the only success criterion
```

You can also run them directly inside the project directory (omitting `--project`), or do it all in one go with `migrate <project dir>`.

If interrupted, resume with `status` / `resume`; each step's state is under the target project's `.qt-ohos/`.

### 5. On failure

```powershell
python tools/qt-ohos-run.py analyze-log <log file>
```

After a QOH pattern hits, follow its references into `problems/`; if it's a **new problem this repository has never recorded**, go through the draft process
(`faults/_drafts/_template.md`, with a reproduction demo or log + stack) and hand it to `kb-iterator` to merge.

### 6. Record the results (backfill into the table below this section)

```markdown
| Date | Application | Qt version | Device | Feasibility verdict | Gate result | Time taken | New knowledge captured |
|------|-------------|------------|--------|---------------------|-------------|------------|------------------------|
|      |             |            |        |                     |             |            |                        |
```

**Pass criterion**: `verify` outputs G0–G12 all PASS; or PARTIAL with a clear reason for every gate that didn't pass
(missing environment components / known application-side limitations), with no vague items like "timed out/no output".
