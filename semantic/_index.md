- [qdrag-cancel-cross-platform](qdrag-cancel-cross-platform.md) — The state of cross-platform support for programmatic drag cancellation via QDrag::cancel(): Windows and X11 implement it (an OLE flag / the QBasicDrag event loop), while macOS (Cocoa) and OHOS do not (cancelDrag falls through to a Q_UNIMPLEMENTED no-op). On OHOS, calling it doesn't crash or hang but silently does nothing, and exec returns once the native drag ends naturally. Includes a demo extending the official draggableicons example and a file:line evidence chain for each platform.
- [qt-harmonyos-accessibility](qt-harmonyos-accessibility.md) — The Qt OHOS accessibility (a11y) bridge and how to enable it: libqohos contains QOhosPlatformAccessibility (a QPlatformAccessibility subclass) that publishes Qt's QAccessible widget tree to the OHOS accessibility framework through each QWindow's XComponent native ArkUI_AccessibilityProvider (via callbacks such as findAccessibilityNodeInfosById). The bridge is off by default and is enabled by the [boolean launch Want parameter io.qt.experimental.enableA11ySupport] (aa start --pb io.qt.experimental.enableA11ySupport true) — not by an env variable, an appArg, or a system screen reader. Once enabled, uitest dumpLayout -b <bundle> returns the complete Qt widget tree (QApplication/QWidget/QPushButton/QLabel + text + bounds); the DevEco MCP get_app_ui_tree goes through the ArkUI inspector and only reaches the XComponent node (no Qt widgets).

- [qt-harmonyos-api](qt-harmonyos-api.md) — Key Qt API compatibility points for HarmonyOS porting: argv differences; choosing a child-process approach per scenario (headless can use QProcess / a Qt UI uses startAppProcess / a non-Qt UI uses startAbility); window model differences (QDialog/Popup are subwindows); modality only applies to subwindows; winId() isn't a native handle; the public path to an OHNativeWindow* via setSurfaceConsumer; hide() has different semantics; setMask() only works on subwindows; closeEvent may come from the system lifecycle. Platform detection: Qt.platform.os returns "linux" on HarmonyOS (upstream's os() has no Q_OS_OHOS branch) — use pluginName for now, and an upstream fix is recommended. Device type detection: Qt exposes no public device-type interface; QtCore's private QOhosDeviceInfo (Q_CORE_EXPORT, includable and linkable, but only three tiers — 2in1/tablet/phone — and essentially a cache of @ohos.deviceInfo) is usable, though applications are better off calling @ohos.deviceInfo directly through Node-API.

- [qt-harmonyos-pyqt-status](qt-harmonyos-pyqt-status.md) — Feasibility status of PyQt5 for HarmonyOS: verified feasible via pyqt5-demo (Qt 5.15.16). The architecture is identical to standard C++ Qt (the libqohos.so QPA plugin); the only difference is that the C++ launcher layer embeds a CPython 3.12 runtime to interpret Python scripts. It depends on DevPython-OH (a cross-compiled CPython) and PythonForArkUI (the PyQt5 site-packages). Known pitfalls: openblas needs a binary patch, sys.exit() produces appspawn crash logs, and only tablet/2-in-1 are supported.
- [qt-harmonyos-qt6-status](qt-harmonyos-qt6-status.md) — Qt 6 HarmonyOS porting status: qtbase dev has merged HarmonyOS support (Gerrit 733351), the minimum SDK is API 20 (HarmonyOS 6.0.0), and it uses the CMake build system. **The Qt 6.12.0 Windows superbuild is verified (2026-07-13)**: a MinGW host + an OHOS Clang target, with the gallery demo running on a real device ("Widget Gallery Qt 6.12.0"). **⚠️ Major correction 2026-07-25: the Qt 6.12 prebuilt installer SDK is a complete distribution** (libQt6Quick.so/Multimedia/Charts/3D/OpenGL/DataVisualization/Bluetooth/Location/Sensors/SerialBus/UiTools/Core5Compat are all present, as is the full QtQuick qml runtime), missing only WebEngine/DBus/Wayland/Pdf/Script. This page's older notes that "non-qtbase hasn't started", "Quick .so absent", and "Multimedia missing" are outdated records from the **source superbuild (strategy B)** era and don't hold for the **prebuilt (strategy B′)** path. The second batch of 10 applications (extending to modules such as opengl/qml/uitools) all building successfully corroborates this. **⚠️ beta3 re-check 2026-08-25**: Qt6HarmonyExtras is a standalone module again (libQt6HarmonyExtras.so + cmake, with the public headers being only exports/version stubs and all 16 functional headers private `_p.h`) — overturning the beta2 conclusion that it "doesn't exist as a standalone module". File permission granting = QtCore's public `QPermissions` API (which has no file permission types — only location/calendar/contacts/bluetooth/camera/microphone) + the private `QtHarmonyExtras::FileShare::persistPermission` API (corresponding to HarmonyOS's `@ohos.fileshare`). - [qt-harmonyos-window-model](qt-harmonyos-window-model.md) — The Qt QPA adapter for ArkUI Window/XComponent: a MainWindow (with a dock/task icon and an independent lifecycle) vs. a Subwindow (no dock entry, belongs to the main window, and closes/minimizes/restores with it). Covers the QOhosFunctions API, 6 code patterns, floating windows, fullscreen rules, embedded subwindows, and cross-process embedding. Also includes [activation semantics]: activateWindow() → @ohos.window.shiftAppWindowFocus (not showWindow!) taking ~94 ms asynchronously, the D1 no-op gap (silently ineffective when there's no focus_window), and focus state ≠ activation state (a grayed title ⇒ no focus ⇒ Tab doesn't respond).
