01

四实体图模型

问题的本质是图：一个应用层表现可指向多个根因（all_of 叠加致病 / any_of 任一即可）；根因之上挂临时方案与上游跟踪单。下面是真实数据子集（4 条因果链）：

症状 S ──causes──▶ 根因 C ◀──targets── 方案 W ／ ◀──tracks── 跟踪单 T 示例：S-0005 一图多因（all_of） · C 节点按处置分类着色
causes（S→C，多因 all_of / any_of） targets（W→C，方案挂靠根因） tracks（T→C，上游单挂靠根因） depends_on（C→C，跨根因阻塞，仅实证可连） ⬥ 闭环：defect（外部责任）= W(adopted) + T(在跟) 才算临时了结；limitation/应用 = W；缺口向上传播至症状
02

定性分水岭 × 处置分类派生

nature（是缺陷还是规格）是根因的第一定性：defect 会修、limitation 规格如此只能绕；disposition（处置分类）回答开发者视角"我该怎么办"——由 nature × responsible 自动派生，不入真源、无双写。

R1responsible = app → 应用使用问题（应用误用，非框架问题）app-usage
R2nature = limitation → 鸿蒙必须适配（改自己的代码，无上游修复可等）must-adapt
R3defect × qt-port / qt-upstream → Qt 问题（等修复 / 本地补丁 / 提 QTBUG）qt-defect
R4defect × ohos-runtime / ohos-ndk / ohos-toolchain → 系统问题（等版本 / 提华为侧单）system-defect
R5defect × third-party → 三方库问题（等三方版本 / 换库）third-party
R6其余（nature = undetermined）→ 待定性；上游定性后自动落入 R1–R5（CID 不变）undetermined
Ddefect（11） —— 会修：跟 fix_version / 上游单 / 复核计划
Llimitation（4） —— 规格如此：给替代方案 + evolution 演进观察
Uundetermined（3） —— 等上游定性：同一状态机，双语义解读

03

三类实体 · 各一套状态机

状态即事实的记录：修复到达（T released）自动提示推进 C；验证通过才退役 W；回归复现退回 open 而 CID 不变。

C根因 · 生命周期regression → open（FID 不变）
open→ diagnosed→ workaround→ reported→ fix-confirmed→ verified→ closed
limitation 旁路：diagnosed → watching（演进观察）→ wontfix（规格稳定终态）；verified 后须完成退役动作（撤 workaround / 关联页注记 / 移入已了结）才 closed
W临时方案 / 替代方案 · 可用性独立于流转状态
proposed→ tested→ adopted→ retired
每条 W 必填 retire_when（退役条件）——修复到达并验证后退役，撤除绕过代码
T跟踪单 · 修复版本的权威来源（fix_version）
draft→ submitted→ accepted→ fixed→ released→ closed dup / wontfix
tracker ∈ qt-bug（QTBUG-xxx）/ ohos-issue / gitee / partner / forum；一个 C 可挂多张单（Qt 侧 + 华为侧）
CHAIN CLOSURE — 链路完备性（闭环规则）
defect（外部责任）临时了结 = W(adopted) 且 T(在跟) ｜ limitation / 应用问题 = W(adopted) ｜ undetermined = W（定性后 T 转硬要求） ｜ 缺口向上传播：缺单 / 缺方案 / 双缺 ｜ S=resolved 而链有缺 → ERROR
当前分布：根治 1 · 临时了结 6 · 未闭环 11（缺单 7 · 缺方案 2 · 双缺 2） ｜ review → 未闭环（待补齐）清单

05

问题确认 · 证据门禁

没有证据的转述/猜测，不得定性为 Qt 框架问题——由 C 页必填字段 evidence_type 声明，check 机器强制。

TYPE形态适用
demo复现 demo（最小 ohos 工程，七原则）运行时行为异常首选
logs调试日志+栈：hilog / cppcrash·jscrash / 探针 / 构建错误原文无 demo 时必须
bothdemo + 日志最强证据
source源码 file:line 引用链仅静态可判定类（Qt 侧 defect 用之收 WARN）
docs官方文档 / 规格链接limitation 专用
QT 框架侧 DEMO 硬性要求
复现逻辑集中在单个 main.cpp（ohos 工程仅 QAbility 胶水壳，可直接粘贴进 qt-bug）+ 复现步骤编号到操作级（每步预期 + expected vs actual）——无步骤视为未完成。
E1defect 的 evidence_type 禁止 docs（不得仅凭文档定性缺陷）
E2limitation 限定 docs / source / logs
E3在跟上游单的 defect/undetermined 必须 demo/logs/both —— 对齐 qt-bug-report 可复现性 HARD 闸门：无可复现材料的单据不提交
① 最小化 ② 自包含可构建 ③ 确定性优先 ④ 对照性 ⑤ 纯净根因 ⑥ 携带诊断输出 ⑦ 版本留痕

无 demo 降级通道：日志 + 栈 + 采集环境三件套，C 页注明"依据日志定性"。

协作草稿 → 主编门禁 → 合入

协作者按提交清单投草稿（格式宽松、不占编号）；主编六步门禁全留痕——复现 demo 必测，未复现不合入。

② 环境三件套
③ 证据：复现 demo 或 日志+栈
④ 查重声明
