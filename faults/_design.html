01

The four-entity graph model

The problem is essentially a graph: one application-layer behavior can point to several causes (all_of: they only produce it combined / any_of: any one is enough); workarounds and upstream tracking tickets hang off the causes. Below is a subset of real data (4 causal chains):

Symptom S ──causes──▶ Cause C ◀──targets── Workaround W / ◀──tracks── Ticket T Example: S-0005, one symptom with several causes (all_of) · C nodes are colored by disposition
causes (S→C; multiple causes all_of / any_of) targets (W→C; workaround attached to a cause) tracks (T→C; upstream ticket attached to a cause) depends_on (C→C; cross-cause blocking, only connected when evidenced) ⬥ Closed loop: a defect (external responsibility) is only temporarily resolved with W(adopted) + T(tracked); limitation/app = W; gaps propagate up to the symptom
02

The nature watershed × derived disposition

nature (defect or limitation) is the first classification of a cause: a defect gets fixed, a limitation is how the platform works and can only be worked around; disposition answers the developer's "what should I do" -- derived automatically from nature × responsible, not stored in the source of truth, no double-writing.

R1responsible = app → Application usage issue (application misuse, not a framework problem)app-usage
R2nature = limitation → Must adapt for HarmonyOS (change your own code, no upstream fix to wait for)must-adapt
R3defect × qt-port / qt-upstream → Qt issue (wait for the fix / local patch / file a QTBUG)qt-defect
R4defect × ohos-runtime / ohos-ndk / ohos-toolchain → System issue (wait for a release / file a ticket with Huawei)system-defect
R5defect × third-party → Third-party library issue (wait for a third-party release / switch libraries)third-party
R6Everything else (nature = undetermined) → Pending classification; falls into R1–R5 automatically once upstream classifies it (the CID stays the same)undetermined
Ddefect (11) —— will be fixed: track fix_version / upstream ticket / review plan
Llimitation (4) —— by specification: provide an alternative + watch the evolution
Uundetermined (3) —— awaiting upstream classification: the same state machine, read with two meanings

03

Three entity types · one state machine each

A status is a record of fact: a fix arriving (T released) automatically prompts advancing C; W is retired only after verification passes; a regression goes back to open with the same CID.

CCause · lifecycleregression → open (FID unchanged)
open→ diagnosed→ workaround→ reported→ fix-confirmed→ verified→ closed
limitation side path: diagnosed → watching (watching the evolution) → wontfix (stable end state of the specification); after verified, the retirement steps must be completed (remove the workaround / annotate related pages / move to resolved) before closed
WWorkaround / alternative · usability is independent of the progression status
proposed→ tested→ adopted→ retired
Every W must have retire_when (retirement condition) -- retired once the fix arrives and is verified, removing the bypass code
TTracking ticket · the authoritative source of the fix version (fix_version)
draft→ submitted→ accepted→ fixed→ released→ closed dup / wontfix
tracker ∈ qt-bug (QTBUG-xxx) / ohos-issue / gitee / partner / forum; one C can have several tickets (Qt side + Huawei side)
CHAIN CLOSURE — CHAIN COMPLETENESS (THE CLOSED-LOOP RULE)
defect (external responsibility) temporarily resolved = W(adopted) and T(tracked) | limitation / application issue = W(adopted) | undetermined = W (T becomes a hard requirement once classified) | Gaps propagate upward: missing ticket / missing workaround / both missing | S=resolved with gaps in the chain → ERROR

The only sources of truth are _data/*.yaml and the cause pages; the full graph and the registry are all rebuilt by the machine -- reverse-lookup indexes, aggregate overviews and view counts are derived automatically; no two-way sync means no drift.

05

Problem confirmation · the evidence gate

Hearsay/guesses without evidence may not be classified as Qt framework problems -- declared by the required C page field evidence_type and machine-enforced by check.

TYPEFORMAPPLIES TO
demoRepro demo (minimal ohos project, seven principles)Preferred for runtime behavior anomalies
logsDebug logs + stack: hilog / cppcrash·jscrash / probes / verbatim build errorsRequired when there is no demo
bothdemo + logsThe strongest evidence
sourceSource file:line reference chainStatically decidable issues only (a Qt-side defect using it gets a WARN)

HARD DEMO REQUIREMENTS FOR QT FRAMEWORK-SIDE ISSUES
The repro logic is concentrated in a single main.cpp (the ohos project is only the QAbility glue shell, so it can be pasted straight into a qt-bug) + repro steps numbered down to the action level (expected result per step + expected vs actual) -- without steps it is considered unfinished.
E1A defect's evidence_type may not be docs (a defect may not be classified from documentation alone)
E2limitation is restricted to docs / source / logs
E3A defect/undetermined cause with a tracked upstream ticket must have demo/logs/both —— matching the qt-bug-report reproducibility HARD gate: tickets without reproducible material are not filed
① Minimal ② Self-contained and buildable ③ Determinism first ④ Contrast ⑤ Clean root cause ⑥ Carry diagnostic output ⑦ Record versions

Degraded path without a demo: the logs + stack + collection environment triple; the C page states "classified from the logs".

06

Collaborative draft → editor's gate → merge

Contributors submit drafts per the submission checklist (loose format, no ids consumed); the editor's six-step gate leaves a full trace -- the repro demo must be tested; not merged unless reproduced.

faults/_drafts/

Contributor submission checklist (required):
① verbatim symptom (logs not paraphrased)
② environment triple
③ evidence: repro demo or logs + stack
④ duplicate check statement
for limitations, an official documentation link can replace the demo

▶
  1. Duplicate check —— if the S/C exists, turn it into a supplement to the existing node; no duplicate pages
  2. Repro test —— defect/undetermined: the demo must be tested; limitation: verify the documentation link; not merged unless reproduced
  3. Human verification —— evidence chain / nature classification / responsible layer / facts (leave blank rather than invent) / sanitization
  4. Repro trace —— the editor's reproduction result is recorded in the first row of the C page's "Version verification log"
  5. promote —— split into S/C/W/T source-of-truth records, ids assigned by the editor; delete the draft
  6. build gate —— zero ERRORs + backfill refs in related pages
▶
PROMOTED → SOURCE OF TRUTH

S/C/W/T each go in their place, and build rebuilds the full graph and the registry; review lists drafts awaiting review, and rejected drafts are kept to prevent resubmission.
