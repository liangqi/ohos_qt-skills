# AGENTS.md

This file is the **behavioral contract** for agents working in this repository (`CLAUDE.md` is a verbatim copy; `_scripts/verify.sh` strictly checks that the two match).

> **This repository is a Qt → HarmonyOS porting engineering repo**: a knowledge layer (facts for humans) + a machine layer (criteria for tools) +
> an execution layer (runnable CLIs and gates) + a governance layer (contracts and self-checks). It is not a read-only documentation set;
> any task may produce code changes, persisted state, and captured knowledge at the same time.

---

## First use (required reading for agents)

If this is the user's first time using this repository, or `ENV.local.md` doesn't exist, and the task needs the local toolchain (build / install on device /
signing / SDK compilation), you **must** first run `skills/kb-init/SKILL.md`: it detects DevEco Studio, the HarmonyOS
SDK, and the Qt source/SDK, guides installation of missing dependencies, generates `ENV.local.md`, and validates that it works.

**Trigger keywords**: initialize, configure the environment, first time using this, setup, install, `ENV.local.md` doesn't exist.

Pure lookup tasks (reading knowledge pages, checking API support) **do not need** initialization.

## Sources of truth and write permissions

| Layer | Who may write | Rules |
|-------|---------------|-------|
| Knowledge source of truth (`semantic/` `procedural/` `episodic/` `problems/` `faults/` `knowledge/`) | Only `kb-iterator` | Business agents may only submit drafts; after changing `knowledge/` or `faults/`, derived artifacts must be rebuilt |
| Execution layer (`tools/` `portgraph/` `templates/`) | Code contributors | Changes must come with tests and must not loosen gate criteria |
| Target project (the user's application) | `qt-app-porting` / `qt-sdk-forge` | Only tracked modifications, written to `.qt-ohos/changes.json` and patches |
| Index (`_index/`), README, SKILL, AGENTS | Maintainers | Count changes must be synced; `tests/test_kb_consistency.py` catches mismatches |

**The machine layer is a projection of the knowledge layer, not a second source of truth**: `refs.problems` in `knowledge/errors/*.yaml` must point to
an existing `problems/` page; `faults/_graph.yaml` and `_registry.md` are generated by `tools/faults-build.py build`
and must not be edited by hand.

## Execution discipline (mandatory)

- **A single success criterion**: application migration is judged by G0–G13 of `python tools/qt-ohos-run.py verify`, the SDK by
  SV0–SV8 of `qt-sdk-run.py verify`. Building successfully ≠ successful migration; `TIMEOUT` is never PASS, and neither are `SKIP` / `NOT_RUN` (not tested ≠ passed).
- **Machine-match logs first**: read knowledge pages only after `analyze-log` hits a QOH pattern; don't skip matching and guess.
- **Changes are tracked**: all automatic modifications go into `.qt-ohos/changes.json` and patches; do not blindly widen
  `Q_OS_LINUX` guards (`Q_OS_LINUX` already holds on HarmonyOS: Qt 6.12+ defines `Q_OS_HARMONY` and derives
  `Q_OS_LINUX` from it, and the Qt 5.15 kit additionally has `Q_OS_OHOS`); do not comment out functional code to get the build to pass.
- **Gates check content, not file existence**: G4 reads each artifact and asserts `ELF64/AArch64/DYN`; G5 unpacks the HAP and checks the
  `DT_NEEDED` closure (import libraries such as `libssl.so.3` don't get into the HAP automatically); G2 only accepts "handled"
  markers that carry evidence; G8 is at most PARTIAL without `bundle_name` configured; G13 checks for strong undefined symbols in the HAP (only SKIP without a sysroot;
  advisory by default, reporting PARTIAL; only FAIL with `config set undefined_gate strict`);
  G6/G7/G8 records are bound to the HAP fingerprint and device serial number; mismatches are marked `STALE` and counted as FAIL;
  G10's `smoke-interact` is only machine evidence collection;
  the authority for the human verdict is not delegated.
- **Tool availability pre-check**: before build/install/signing/logs, locate and verify `devecocli`, `hdc`, and the Qt OHOS SDK
  (`devecocli` order: `DEVECO_CLI` in `ENV.local.md` → PATH → npm global → bundled with DevEco;
  it isn't necessarily installed with DevEco Studio). If unavailable, stop, report, and give the install command; do not continue with guessed paths.
- **End-of-turn discipline**: in non-interactive sessions (`opencode run` / `claude -p`, etc.) the session exits when the turn ends,
  and no mechanism will wake you up. Do not "dispatch a background agent and then wrap up waiting"; long tasks must wait synchronously or run sequentially within this turn;
  do not output a summary and stop before reaching the `verify` terminal state or a human confirmation point; to abort, persist state to `.qt-ohos/` and state how to resume.
- **Derived views must not be edited by hand**: `_index/_dashboard.md` is generated by `python _scripts/gen-dashboard.py` (page count/active count/problems/fault scale); to change numbers, change the source of truth and rerun the script; `verify` C9 catches hand edits.
- **Rebuild after changing the fault library's source of truth**: run `python tools/faults-build.py build`, with zero ERRORs from `check`;
  use `review` to scan for due items and status progression.
- **Merging drafts goes through the editor-in-chief gate** (`faults/_index.md` §6): defect/undetermined items **must have a reproduction demo that has been run**,
  human verification (evidence chain/classification/layer attribution/facts/sanitization), and the reproduction result recorded in the first row of the C page's "Version verification record" before they can be promoted.
- **Evidence standard**: classifying a problem as Qt-framework-side requires a reproduction demo or debug log + stack (C page `evidence_type`;
  statically decidable items may use the source exception, flagged with a warning); pure hearsay/guesses are not accepted. Qt-side demos must concentrate the reproduction logic in
  a single `main.cpp` (the ohos project is only a glue shell) and spell out numbered reproduction steps.
- **Closed-loop chains** (`faults/_index.md` §4): a defect's "workaround" must have both an adopted workaround (W adopted)
  and an open tracking ticket (T); limitations and application issues must have an adopted workaround; gaps propagate upward, and S claiming resolved while the chain has gaps → ERROR.
- **End-of-work self-check**: `python _scripts/ci.py` must pass (equivalent to `bash _scripts/ci.sh`; use the former on Windows without bash);
  changing numbers in docs without changing the facts turns the gate red. Derived numbers in README/TESTING are synced from the source of truth by
  `python _scripts/sync-counts.py` (`--check` only checks); don't edit them by hand.

## Branches and delivery

- `trunk` is the mainline and the source of stable releases; develop on your own development branch, and pass the gates before merging back into `trunk`.
- Old branches (`main`, `bitfun-release`, etc.) are **frozen**; do not commit on them.
- Commit messages should state clearly "which facts/criteria changed"; don't just write "update".

## To-dos and progress

- `TODO.md`: the checked-in to-do template (structure conventions; no real entries).
- `TODO.local.md`: your actual personal to-dos and progress (gitignored, never checked in).
- For multi-step tasks, update `TODO.local.md` at each phase transition; pure lookup tasks need no sync.
