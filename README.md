# The Qt for HarmonyOS knowledge base (developer edition)

> A HarmonyOS porting reference knowledge base for **Qt application developers**. It distills hands-on Qt for HarmonyOS experience into structured Markdown knowledge pages so you hit fewer pitfalls and diagnose problems faster when moving a Qt application to HarmonyOS.
>
> This is the **developer edition**: generated by trimming a larger internal workflow knowledge base with `_scripts/kb-dev-edition.sh`, keeping only the technical content useful to application developers. It contains no internal team collaboration, commercial support, or supply-chain processes, and no source-level Qt framework debugging methodology.
>
> **Current version**: v2.2.1 (2026-08-29) | [Changelog](CHANGELOG.md) | [Capability spec](#capability-spec)

## Capability spec

> This section is the formal functional specification of the external knowledge base (developer edition): what it **can** do, its input/output contract, and its versioning and compatibility policy.
> The versioned object = the whole external repository bundle (the public Qt subset + the embedded ohos-common-kb + the kb-init skill + the root documents), not an individual KB.

### Feature list

This knowledge base covers **12 categories of public task** (the routing codes are in `_index/_task-routing.md`):

| Routing code | Task | Entry page | Expected output |
|--------------|------|------------|-----------------|
| [A] | Porting an application to HarmonyOS | `procedural/qt-app-harmonyos-migration` + `semantic/qt-harmonyos-porting-workflow` | Feasibility assessment → project creation → the 8-step migration → build verification |
| [B] | API replacement lookup | `semantic/qt-harmonyos-api-mapping` (12 mapping categories) + `qt-harmonyos-code-patterns` | A replacement plan + before/after code |
| [C] | Qt module support lookup | `semantic/qt-harmonyos-modules` | Whether it's supported + the version (5.12/5.15) + alternatives |
| [D] | Platform limitation lookup | `semantic/qt-harmonyos-platform-limits` | A description of the limitation + the QTBUG number + a workaround |
| [E] | Build troubleshooting | `semantic/qt-harmonyos-build-run-workflow` §the four-step triage + `problems/_lookup` | Error classification → root cause → fix steps |
| [F] | Window problems | `semantic/qt-harmonyos-golden-rules` §2 + `qt-harmonyos-window-model` | An explanation of the rule + the fixed code |
| [G] | Lifecycle | `semantic/qt-harmonyos-lifecycle` | A description of the behavior + code examples + enum paths |
| [H] | QtOhosExtras APIs | `semantic/qt-ohos-extras` (145+ APIs) | The API signature + its purpose + a usage example |
| [L] | Qt6 status | `semantic/qt-harmonyos-qt6-status` | The current status + known differences + items still to verify |
| [M] | Third-party libraries | `semantic/qt-harmonyos-third-party-libs` | The cross-compilation method / deployment steps / compatibility |
| [N] | Toolchain | `semantic/deveco-mcp-toolchain` + `deveco-cli-commands` | Installation/configuration, or a headless build recipe |
| [Q] | Demo generation | `procedural/demo-generation` (for Qt+CEF/WebEngine demos, see §3.3 + `qt-cef-ohos-dev-guide` + `tools/kb-cef-graft.py`) | Requirement → design → project → code → build → documentation; for a Qt+CEF demo, `tools/kb-cef-graft.py --run` does it all |

**Bundled tools**: `skills/kb-init/` — environment detection (DevEco/SDK/Qt source) → guided installation of missing dependencies → generating `ENV.local.md` → validating the environment. `tools/kb-cef-graft.py` + `tools/kb-cef-graft.config.example.json` — the Qt+CEF demo grafting script (grafts CEF onto the Qt OHOS template; `--run` does signing + installation + launch + crash checking, with all environment configuration in the config file; see `procedural/qt-cef-ohos-dev-guide.md`).

**The embedded common-KB subset**: `ohos-common-kb-public/` provides general HarmonyOS platform knowledge (ArkTS/ArkUI/NAPI/the Stage model/DevEco toolchain basics) that complements the Qt knowledge.

### Input / output contract

| Input | Processing | Output |
|-------|------------|--------|
| A natural-language request (fed to an AI tool) | Task routing → scan the iron rules → load pages as needed → synthesize | A replacement plan + code / module status / a limitation + QTBUG / an error solution / a build recipe |
| Direct browsing (human / Obsidian) | `_dashboard` for the overview → `_map` for the summaries → open a self-contained page | A structured technical reference |

The fixed entry chain: `_index/_task-routing → semantic/qt-harmonyos-golden-rules → _index/_map → the pages you need → follow refs deeper`. For an error, step one is always `problems/_lookup.md`, searched by error code or symptom.

### Versioning and compatibility policy

- **Version numbers**: [SemVer](https://semver.org/) `vMAJOR.MINOR.PATCH`, where the versioned object is the whole external repository bundle. The baseline is `v2.0.0` (2026-08-19); v1 was never backfilled.
- **MAJOR (breaking)**: deleting/relocating a page users depend on, changing `audience` from public to internal, directory reshuffles that break old links, or an iron rule / API mapping being disproven and reversed.
- **MINOR (content additions)**: a new page/section/API mapping entry/task type, or a newly embedded KB or skill.
- **PATCH (content corrections)**: typos and wording fixes, updated error solutions, Qt reference version bumps.
- **Pinning a version**: `git clone --branch vX.Y.Z <this repository>`.
- **Changelog**: see [CHANGELOG.md](CHANGELOG.md).
- **Reproducibility**: each release generates a `RELEASE-MANIFEST.yaml` (recording the source KB's git SHA + `content_tree_sha256` + page counts), so a release's content can be reproduced from the `source_kbs` SHAs.
- **Qt framework validation baseline**: Qt 5.15.16 (tqtc/harmonyos-5.15.16, 962aa625) / Qt 5.12.12 (tqtc/harmonyos-5.12.12, 613336de).

## Quick start

### First use: run the initialization skill

After cloning this repository, tell your AI tool "initialize the knowledge base" or "help me configure the environment", and the agent will run the initialization flow in `skills/kb-init/` to set everything up.

The initialization skill walks you through:
- Detecting the current environment (DevEco Studio, the HarmonyOS SDK, the Qt source, and so on)
- Guiding installation of missing dependencies
- Generating `ENV.local.md` (local path configuration)
- Validating that the environment works

### Option 1: let an AI tool use it automatically (recommended)

This library drives AI tools through `CLAUDE.md` / `AGENTS.md` (identical content). Just open your tool in the repository root:

| Tool | How to hook it up |
|------|-------------------|
| Claude Code | Open the repository root; it reads `CLAUDE.md` automatically |
| Codex / OpenCode | Open the repository root; it reads `AGENTS.md` automatically |
| Cursor | Create `.cursorrules` containing: `Please read and follow the knowledge base structure defined in _index/_map.md` |
| Windsurf | Create `.windsurfrules` with the same content |
| ChatGPT / others | Upload `_index/_map.md` + the relevant knowledge pages manually, or paste `CLAUDE.md` into the system prompt |

Once connected, just ask questions in natural language; the AI follows "task routing → scan the iron rules → load knowledge pages as needed → give you a plan". When it hits an error it checks `problems/_lookup.md` first.

### Option 2: browse it yourself

Start from `_index/_dashboard.md` (the dashboard, for the overview) or `_index/_map.md` (the knowledge map, one sentence per page), then open the `.md` files in each domain directory as needed. Every file is a self-contained unit of knowledge.

### Option 3: Obsidian

Open this folder as a vault. Install the Dataview plugin for advanced frontmatter queries, and use Graph View to see the knowledge graph.

## How it works: the path taken once a task arrives

The AI's processing order is fixed, so you don't have to remember it:

```
Your request
  → _index/_task-routing.md   match the task type, determine the workflow and required pages
  → semantic/qt-harmonyos-golden-rules.md   scan the 35 iron rules (to avoid known pitfalls)
  → _index/_map.md            judge relevance from the summaries and read only what's needed
  → follow the refs field for cross-references     for deeper context
```

The most frequently used entry points:

| What you want | Which page |
|---------------|------------|
| The full knowledge overview | `_index/_map.md` |
| API replacements | `semantic/qt-harmonyos-api-mapping.md` + `qt-harmonyos-code-patterns.md` |
| Module support | `semantic/qt-harmonyos-modules.md` |
| Platform limitations | `semantic/qt-harmonyos-platform-limits.md` |
| Project structure / templates / CMake | `semantic/qt-harmonyos-project-structure.md` |
| Practical builds (producing a HAP) | `procedural/qt-ohos-concrete-build-recipe.md` |
| The full build-and-run process / DevEco MCP | `semantic/qt-harmonyos-build-run-workflow.md` |
| An error you hit | **Read `problems/_lookup.md` first**, searching by error code/symptom |

### How to use the error library

When you hit a build/deployment/runtime error, step one is `problems/_lookup.md`: search by error code, error message keyword, or symptom, and read the matching problem file for the solution. `problems/` records pitfalls actually hit in practice (CMake find_package failures, dlopen rejecting writable paths, the QPA plugin not being deployed, signature mismatches, and so on) — not the platform limitations from the official Qt documentation, which live in `semantic/qt-harmonyos-platform-limits.md`.

## Local environment configuration

Knowledge pages refer to local paths by variable name (such as `QT5_15_OHOS_SDK` and `OHOS_SDK_NATIVE`) rather than hard-coding them. Running the `skills/kb-init/` initialization skill generates `ENV.local.md` automatically, or you can replace the `<PLACEHOLDER_*>` values in `ENV.md` with your own paths by hand. What you need:

- **DevEco Studio + the HarmonyOS SDK** (API 17/20) — provides the OHOS clang, sysroot, hvigorw, and emulator
- **The Qt 5.12 / 5.15 HarmonyOS source** (the tqtc/harmonyos branches, publicly available) — see "Obtaining the source" in `ENV.md`
- **MinGW + Strawberry Perl** (for building Qt on Windows)
- A built **Qt OHOS SDK** (the `CMAKE_PREFIX_PATH` your application links against)

> Application developers can usually start as soon as they have the prebuilt Qt OHOS SDK their team distributes; you only need the source + MinGW + Perl if you want to rebuild the Qt libraries yourself.

### Ways to obtain the Qt source

Pick a path depending on whether you have a Qt commercial license:

| Scenario | How to obtain | Notes |
|----------|---------------|-------|
| **Have a Qt commercial license** | `git clone https://codereview.qt-project.org/qt/tqtc-qt5` | Requires a Qt commercial license; gives you the latest patches and full history |
| **No license (open source)** | https://gitcode.com/ohos-qt/qt-harmonyos-src | Open-source code, no license required |
| **Only need the prebuilt SDK** | https://gitcode.com/ohos-qt/qt-harmonyos-src/releases | Includes SDKs for Windows/macOS/HarmonyOS |

For detailed steps, see the "Ways to obtain the source" section of `ENV.md`, or run the `skills/kb-init/` initialization skill to be guided automatically.

The prebuilt SDK releases page has builds for these platforms:

| Platform | Rendering backend | Notes |
|----------|-------------------|-------|
| Windows | Desktop GL | Windows development, Desktop GL rendering |
| Windows | GLES | Windows development, GLES rendering |
| macOS | Desktop GL | macOS development, Desktop GL rendering |
| macOS | GLES | macOS development, GLES rendering |
| HarmonyOS | GLES | Runs on HarmonyOS devices, GLES rendering |

## Design philosophy

- **Compilation rather than retrieval** — following [Karpathy's LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f), raw experience is distilled into structured knowledge pages
- **Layered loading** — modeled on Claude Code's hierarchical context mechanism: the index layer is always loaded, and knowledge pages are loaded on demand
- **Files as data** — plain Markdown + Git, with zero infrastructure dependencies
- **Typed memory** — drawing on cognitive science, knowledge is split into four types plus an error library
